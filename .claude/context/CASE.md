# Кейс М.Видео: автозаполнение характеристик товаров — требования

Источники: страница кейса (hub.gigaschool.ru/.../cases/magnit-attributes) и презентация кейсодателя
«Извлечение атрибутов из карточек товаров» (`data/raw/case_brief.pdf`, 18 слайдов). Полный текст страницы: [sources/case_page.txt](sources/case_page.txt).

## Задача одной фразой
Пайплайн: текстовая карточка (заголовок, описание, атрибуты продавца) → определить нужные атрибуты → извлечь →
нормализовать к каноническому виду → для каждого значения указать **уверенность**. Только текст, изображения не используются.

## Зачем бизнесу (слайд 2)
Атрибут заполнен → товар попадает в фильтры → выше CTR и конверсия → **рост GMV**. Атрибуты = поиск/фильтры, фичи для рекомендаций,
дедупликация (матчинг одинаковых SKU разных продавцов), сравнение/ценообразование/ассортимент.
«Извлечение атрибутов — это про деньги в поиске и каталоге, а не ML-упражнение ради метрики».

## Почему сложно (слайды 4–5)
Огромная таксономия (тысячи категорий × десятки атрибутов), длинный хвост редких значений, неоднозначность
(«алый» = «красный» = «red»), масштаб и дрейф (новые SKU и категории каждый день).

## Функциональные ограничения (обязательно соблюсти и ПОКАЗАТЬ)
1. На входе только текст карточки: title + description + атрибуты продавца.
2. Каждое значение → канонический вид + оценка уверенности. В каталог — только надёжные, сомнительные → ручная проверка.
3. **Не выдумывать характеристики** (главный риск LLM): схема вывода, **справочники допустимых значений**,
   проверка, что значение **есть в тексте карточки**, **порог уверенности**.
4. **Стоимость**: LLM на каждую карточку дорого → гибрид: дешёвые методы на типовые случаи, дорогие — только где нужно.
5. **Справедливость**: одинаково хорошо для всех категорий и продавцов (редкие категории и мелкие продавцы не должны страдать).

## Формат решения
- Начать с **базлайна на правилах и словарях**, затем ML-модель или LLM, **показать, что даёт каждый шаг**.
- Ожидаемый ответ кейсодателя (слайд 12): **гибрид — правила для ядра, модели для хвоста, LLM для cold-start**.
- Продакшен-пайплайн (слайд 13): карточка → препроцессинг → извлечение → нормализация → **мэппинг на справочник маркетплейса** → оснащение карточки.
- **Петля обратной связи** (плюс к оценке): ошибки и low-confidence → ручная разметка → дообучение/обновление правил.
- Разметка (слайд 14): active learning, weak supervision (правила как дешёвые лейблы), LLM-assisted разметка, gold-сеты по категориям.

Таблица сравнения подходов из кейса (её стоит воспроизвести на НАШИХ цифрах):

| Подход | Качество на хвосте | Стоимость инференса | Нужно данных | Поддерживаемость | Новые категории |
|---|---|---|---|---|---|
| Правила и словари | Низкое | Очень низкая | Не нужны | Средняя | Хорошо |
| NER (разметка токенов) | Среднее | Низкая | Средне | Средняя | Слабо |
| Дообученный трансформер | Высокое | Средняя | Много | Средняя | Слабо |
| LLM (zero/few-shot) | Высокое | Высокая | Мало | Высокая | Очень хорошо |

Пример результата: Бренд Samsung 0,98 · Объём памяти 256 ГБ 0,95 · Диагональ экрана 6,7 дюйма 0,93 · Цвет чёрный 0,81.

## Шесть обязательных артефактов (комплект сдачи)
1. Код или ноутбук, воспроизводящий решение.
2. README с инструкцией установки и запуска.
3. **EDA**: разбор полей, пропусков, распределений.
4. Пайплайн извлечения: от текста карточки до атрибутов.
5. **Файл с предсказанными атрибутами по каждой карточке**.
6. Финальная презентация: подход, метрики, выводы.
Всё одним репозиторием/архивом, **запуск воспроизводится по README**.

## Метрики успеха
| Метрика | Что показывает | Как считать |
|---|---|---|
| Precision / recall / F1 **по каждому атрибуту** | точность и полнота каждого поля, включая редкие | отдельно по атрибуту на размеченном эталоне |
| Покрытие (coverage) | насколько полнее каталог | доля карточек, где атрибут заполнен |
| Качество с учётом трафика | польза покупателю | метрики взвешены по трафику: атрибуты, по которым чаще фильтруют, весят больше |
| Оценка на эталоне по категориям | работа на редких категориях | gold-сет, размеченный людьми по категориям |
Общая accuracy не подходит — маскирует провалы на хвосте.

## Риски — показать на защите вместе с мерами (слайд 15)
| Риск | Последствие | Меры |
|---|---|---|
| Галлюцинации LLM | ложные атрибуты ломают фильтры | structured output + порог уверенности |
| Стоимость при масштабе | LLM дорого на каждый SKU | дистилляция, кэш, гибридный роутинг |
| Eval не покрывает хвост | метрика красивая, качество плохое | gold-сеты по редким категориям |
| Дрейф новых категорий | падение качества во времени | мониторинг + петля дообучения |
| Несправедливость к продавцам | мелкие SKU хуже обрабатываются | контроль покрытия по сегментам |
«На уровне VP первым делом спрашивают про риски — не прячьте их».

## Данные и обязательные поля
- Датасет карточек из разных категорий (в первую очередь электроника): текст, атрибуты продавца, размеченная часть.
- Обязательные поля: бренд, модель, ключевые характеристики категории.
  - Смартфон: **бренд, модель, объём памяти, диагональ экрана, ёмкость батареи, цвет**.
  - Ноутбук: **бренд, процессор, объём RAM, накопитель, диагональ, цвет**.
- «Точный перечень обязательных полей фиксируется вместе с датасетом» — в выданном архиве отдельного списка нет,
  поэтому перечень для остальных категорий выводим из данных (заполненность в каталоге × спрос в поисковых запросах). Подробно: [DATA.md](DATA.md).
