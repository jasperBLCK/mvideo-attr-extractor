# PRD — выжимка

Источник истины — [docs/PRD.md](../../docs/PRD.md) (версия 15.10, владелец — поток «продукт»). Здесь — сжатие для работы.

**Проблема.** Характеристика заполнена → товар в фильтрах и атрибутной выдаче → CTR, конверсия, GMV. Данные: 1 177 200
описаний; эталон — 546 069 офферов фида в 6 963 категориях; 30,99 млн кликов поиска, ≥ 22,6% — по запросам, где покупатель
сам назвал характеристику (нижняя оценка); у 75% карточек есть только текст; блок продавца у карточек с эталоном — 6,6%;
текст содержит не все значения (смартфоны: диагональ 34–51%, батарея 50%, цвет 42%) → решение обязано говорить «в тексте нет».

**Цель.** В каталог — только надёжные значения (precision ≥ 0,95), сомнительное — модератору с цитатой; LLM — только где нужна.
**В границах:** только текст карточки; смартфоны (761 + 914), ноутбуки (987) + топ категорий по кликам; извлечение, канон,
уверенность, статус, цитата; очередь и петля обратной связи; API, батч, UI, офлайн-оценка.
**Не цели:** изображения, прямая запись в PIM, генерация описаний, интерфейс продавца (после пилота), своя A/B-инфраструктура.

**Пользователи (JTBD, гипотезы):** модератор каталога (проверять только сомнительное с цитатой), категорийный менеджер
(какие фильтры пусты и сколько поиска теряют), продавец маркетплейса (не заполнять поля руками), поиск/рекомендации/матчинг
(канон + уверенность для своего порога). Единица ценности — верно заполненная характеристика, по которой ищут.

**Сценарии.** С1 пакетное обогащение (`attrx extract`, `/api/extract/batch` ≤ 1000) → accepted в PIM, review в очередь,
missing — отчёт продавцу. С2 модерация → `/api/feedback` → `attrx learn` → словари. С3 новая категория: схема в
`taxonomy.yaml` без кода, LLM zero-shot со статусом review. С4 проверка карточки при загрузке + generative UI.
С5 мониторинг и откат категории в тень (план).

**Требования.** FR-1 вход — title/description/seller_attrs · FR-2 категория из id, иначе по тексту · FR-3 обязательные атрибуты
по категориям · FR-4 источники по возрастанию цены, NER и LLM — только хвост · FR-5 нормализация · FR-6 уверенность ·
FR-7 статусы · FR-8 цитата, смещение, альтернативы · FR-9 антигаллюцинации · FR-10 очередь по «вес спроса × (1 − уверенность)»
с отменой · FR-11 обучение на правках · FR-12 батч · FR-13 отчёт качества · FR-14 калибровка и порог · FR-15 UI с generative UI ·
FR-16 конфиги без кода · FR-17 мониторинг дрейфа (план).
NFR: всё в контуре (on-prem LLM, без VPN) · без LLM работает · p95 ≤ 50 мс на карточку без LLM · корпус за ночь без GPU ·
LLM ≤ 20% карточек, повтор бесплатен (кэш) · воспроизводимость · объяснимость · безопасный UI · Docker :8000 · наблюдаемость.

**Контракт выхода** — `ExtractionResult` / `AttributeValue` (канон, unit, display, confidence, status, sources, evidence,
evidence_span, alternatives, required, traffic_weight); файл сдачи — `submission/predictions.jsonl` + `.csv`.
**Доверие:** схема и strict JSON → справочники в промпте → дословная цитата → заземление → порог → человек.
**Раскатка:** офлайн-гейт (K1, K4) → тень 2–4 недели → автопринятие в топ-категориях с аудитом → масштаб; откат категории в тень.
**Экономика:** C_гибрид ≈ p_LLM × C_«LLM на всё», так как CPU-часть ничтожна; повторный прогон — 0 ₽.
**Открытые вопросы к М.Видео:** официальный список обязательных атрибутов; кто заполняет офферы и SLA модерации; база
бизнес-метрик и модерации; допустимый LLM-контур; формат интеграции с PIM; точное значение или бакет фильтра; порог по атрибутам;
можно ли показывать продавцу недостающие поля.
