# Категория карточки по тексту: ML-классификатор поверх правил

**Коротко.** Набор атрибутов зависит от категории товара, но у **74,8% карточек (880 632 из 1 177 200) категории нет**:
нет ни оффера в YML-фиде М.Видео, ни поисковых кликов, только текст. Базлайн на правилах (ключевые слова таксономии)
путает товар с аксессуаром к нему: «Чехол для смартфона» попадает в смартфоны, «Сумка для ноутбука» — в ноутбуки.
Поверх правил работает дешёвая ML-модель: TF-IDF по тексту карточки и двухуровневая линейная модель «раздел каталога →
лист каталога». Классы модели — листья реального дерева каталога, а не категории таксономии. На отложенной выборке
(holdout, 29 504 карточки, в подборе не участвовала):

| | Ключевые слова (правила) | Классификатор |
|---|---:|---:|
| Accuracy категории таксономии (12 категорий + generic) | 0,921 | **0,9998** |
| Macro-F1 категории таксономии | 0,790 | **0,998** |
| Лист каталога (1 087 классов), top-1 / top-3 | — | 0,984 / 0,990 |
| Калибровка уверенности, ECE | — | 0,0001 |
| Скорость, 1 ядро CPU | ~7 500 карт/с | 1 400–1 900 карт/с пакетом, 1–1,3 мс на карточку |

Модель занимает 7,8 МБ: веса в int8 и словарь в JSON, без pickle. Для инференса нужен только numpy, без GPU и сети.
Обучение одной командой `attrx train-category` идёт ~6 минут на 4 ядрах (с подбором α — ~10 минут) и воспроизводит
артефакт бит в бит.

| Требование кейса | Как сделано | Где |
|---|---|---|
| Определить, какие атрибуты нужны карточке | категория по тексту → схема атрибутов категории из `config/taxonomy.yaml` | `src/attrx/category.py` |
| Гибрид: правила для ядра, модели для хвоста | `category_id` из каталога → правило (уверенность 1,0); нет id → классификатор; ниже порога → модератор | раздел 5 |
| Уверенность и порог | калиброванная вероятность (temperature scaling на dev); порог 0,9; ниже порога — проверка с предупреждением | `models/category/meta.json`, раздел 2.4 |
| Стоимость | CPU, ~1 мс на карточку; 880 тыс. карточек без категории — 8–10 мин на одном ядре | `metrics.json` → `throughput` |
| Справедливость | точность одинакова для М.Видео и маркетплейса, для карточек вне фида, для редких категорий | раздел 3.3 |
| Показать, что даёт каждый шаг | правила и модель на одном holdout, по категориям и сегментам | раздел 3 |
| Воспроизводимость | seed, детерминированные сплиты, подбор только на dev, holdout один раз | раздел 6 |

## 1. Зачем

- **Категория определяет схему.** От категории зависят обязательные атрибуты: смартфону нужны память и диагональ,
  холодильнику — объём камер. Если категория определена неверно, извлекаются не те атрибуты: у чехла появится
  «объём встроенной памяти».
- **У большинства карточек категории нет.** Категория известна у 296 568 карточек: 241 355 по офферу фида
  и 55 213 по `seo_id` кликов. У остальных 880 632 карточек нет ничего, кроме текста. Это cold start, о котором
  говорит кейс.
- **Ключевые слова ошибаются на аксессуарах.** Правила ищут подстроку «смартфон»/«ноутбук»/«galaxy» в тексте. На
  карточках без категории правила относят к смартфонам 13,1% карточек, модель — 3,5%. Разница — в основном чехлы,
  защитные стёкла, кабели и термопоты Galaxy, которые правила принимают за смартфоны (раздел 4).

## 2. Как устроено

```
карточка ──► category_id известен (оффер / клики)? ──да──► категория таксономии по category_ids, уверенность 1,0
                 │ нет (74,8% карточек)
                 ▼
  признаки TF-IDF: title — слова 1–2 + символьные 2–5-граммы; описание (300 симв.) + атрибуты продавца — слова 1–2, вес 0,5
                 ▼
  этап 1: раздел каталога (91 класс)          этап 2: лист внутри раздела (1 087 классов всего)
                 ▼
  P(лист) = P(раздел) · P(лист | раздел)  ──►  P(категория таксономии) = Σ P(листья из её category_ids)
                 ▼
  уверенность ≥ 0,9 ──► схема атрибутов категории        < 0,9 ──► лучшая гипотеза + предупреждение → модератор
```

### 2.1 Признаки

Используются три блока TF-IDF. Значение признака равно `(1 + log tf) · idf`. Каждый блок нормируется по L2 и
умножается на свой вес. Словарь строится по 120 тыс. карточек train; n-грамма попадает в него, если встречается
минимум в 2–3 документах.

| Блок | Что | Вес | Зачем |
|---|---|---:|---|
| `title_word` | слова заголовка без чисел + биграммы | 1,0 | «для ноутбука», «чехол для» — биграммы отличают аксессуар от товара |
| `title_char` | символьные 2–5-граммы внутри слов (как `char_wb`) | 1,0 | падежи («холодильника»), опечатки, артикулы (`sm-a556`) |
| `context_word` | первые 300 символов описания (без HTML) + атрибуты продавца «ключ значение», слова + биграммы | 0,5 | заголовки вида «Робот GSS -», где тип товара есть только в описании |

Признаки строит одна и та же функция при обучении и на инференсе (`Featurizer.ids`), поэтому расхождения между
обучением и продом нет. Символьные n-граммы кэшируются по слову, это ускоряет их построение в ~6 раз.

### 2.2 Пространство меток

Пайплайну нужна категория таксономии: 12 категорий и `generic`. Модель при этом предсказывает **лист каталога**, а
категория таксономии получается из листа при загрузке модели. Так сделано по трём причинам:

1. **Таксономия меняется.** Категории добавляются в `config/taxonomy.yaml` через `category_ids`. Отображение
   «лист → категория» применяется при загрузке модели, поэтому новая категория из уже известных листьев работает
   без переобучения.
2. **`generic` — это 90% данных и тысячи разных товаров.** Как один класс он плохо разделим линейно. Как сотни
   листьев он разделяется хорошо, а P(generic) получается суммой их вероятностей.
3. **UI и cold start нужен лист.** Модератор видит «Чехлы для смартфонов», а не просто «прочее». Лист и путь
   в дереве записываются в `ExtractionResult.category_title` и `category_path`.

Состав классов:

- **Разделы (этап 1)** — 91 корень дерева каталога, у которого есть карточки в train.
- **Листья (этап 2)** — 1 000 листьев, самых частых в train, плюс все листья таксономии, у которых в train
  минимум 10 карточек. Они покрывают 95,7% карточек train; всего в train 2 975 листьев.
- **«Прочее в разделе»** — остальные редкие листья раздела, объединённые в класс `other:<id раздела>`. Таких
  классов 87. Модель всё равно сообщает раздел («Прочее: Товары для дома»), и такой класс всегда отображается в
  `generic`.

Из обучения исключены 1 746 карточек с `category_id` вне дерева каталога (например, `seo_id = 0`).

### 2.3 Модель: почему иерархия, линейный SVM и прореживание

Модель — линейный SVM (`SGDClassifier(loss="hinge")`) в схеме one-vs-rest на двух этапах. На этапе 1 он учится
на всех карточках train. На этапе 2 для каждого раздела обучается отдельный классификатор только на карточках этого
раздела. Варианты сравнивались на dev, сравнение по top-1 листа:

| Вариант (dev) | Классов | Обучение | Лист top-1 |
|---|---:|---:|---:|
| Плоский one-vs-rest, 500 листьев + «Прочее» | 594 | 308 с | 0,987 |
| Иерархия «раздел → лист», 500 листьев | 594 | 67 с | 0,986 |
| Иерархия, 1 000 листьев, hinge (выбрано) | 1 087 | 55 с | 0,984 |
| Иерархия, 1 000 листьев, `modified_huber` | 1 087 | 71 с | 0,981 |
| α = 2e-6 / 5e-6 / 1e-5 (подбор в `--search`) | 1 087 | 56 / 50 / 81 с | 0,9834 / 0,9833 / 0,9832 |

Иерархия обучается в 4–6 раз быстрее плоской модели при той же точности (−0,1 п. п.). Причина: этап 2 видит только
карточки своего раздела. Именно это позволило различать 1 000 листьев вместо 500 и уложиться в бюджет обучения.
Время в таблице зависит от загрузки машины, на ней параллельно работали другие процессы. Регуляризация α выбрана
на dev (`attrx train-category --search`); разница между значениями — в четвёртом знаке.

**Прореживание и квантизация.** У каждого класса раздела оставлено 20 тыс. признаков с наибольшим |w|, у каждого
класса листа — 4 тыс. Веса хранятся в int8 с масштабом на класс. На dev:

| Веса | Ненулевых | `model.npz` | dev лист top-1 |
|---|---:|---:|---:|
| без прореживания | 5,81 млн | 8,9 МБ | 0,9836 |
| топ-20 тыс. / 4 тыс. (выбрано) | 4,26 млн | 7,3 МБ | 0,9834 |
| топ-20 тыс. / 2 тыс. | 3,41 млн | 6,2 МБ | 0,9783 |
| топ-10 тыс. / 1 тыс. | 1,92 млн | 4,0 МБ | 0,9738 |

Замер сделан при α = 1e-5. В итоговой модели при α = 2e-6 осталось 3,88 млн весов.

### 2.4 Калибровка и порог

- **Калибровка — temperature scaling на dev.** Модель выдаёт оценки SVM, а не вероятности. Вероятности получаются
  через softmax с температурой для разделов и для листьев внутри раздела. Обе температуры подобраны по минимуму NLL
  на dev: сначала по отдельности, затем совместно по итоговой P(лист). Итог: T(раздел) = 0,32, T(лист) = 1,00;
  совместная подгонка снизила NLL листа на dev с 0,178 до 0,174. В эксперименте при α = 5e-6 ECE листа на dev
  снизилась с 0,014 до 0,005.
- **Уверенность** — калиброванная P(категория таксономии | текст), то есть сумма P(лист) по листьям категории.
  На holdout ECE равна 0,0001 для категории и 0,009 для листа.
- **Порог 0,9.** Он вычисляется как max(минимальный порог с точностью ≥ 0,99 на dev, 0,9). На карточках с
  категорией модель почти не ошибается, поэтому порог по точности вырождается в 0,57. Нижняя граница 0,9 при
  калиброванной уверенности означает: каждая автоматически принятая категория верна с вероятностью не ниже 90%.
  Порог хранится в `meta.json` (`threshold`), правило и цифры — в `metrics.json` (`threshold`).
- **Сколько уходит модератору.** На holdout 0,02% карточек (7 из 29 504). На карточках без категории — 0,12%.
  При пороге 0,99 — 1,0% (раздел 4).

### 2.5 Отображение на таксономию

- **Обычный путь.** При `CategoryClassifier.load(taxonomy=...)` модель читает `category_ids` из объекта `Taxonomy`
  или из `config/taxonomy.yaml` (по умолчанию; можно задать `TAXONOMY_PATH`). Сейчас все 12 категорий таксономии
  имеют `category_ids`, отображено 25 листьев.
- **Временное отображение.** Если у категории нет `category_ids`, листья берутся из топ-25 листьев
  `taxonomy_candidates.json`, у которых название совпадает с названием категории или содержит её ключевое слово.
  Такие листья видны в `clf.provisional_map`. Сейчас этот путь не используется: все категории заданы явно.
- **Листья вне пространства меток.** Если лист из `category_ids` не входит в классы модели, он попадает в
  `clf.unmapped_leaves` и в лог. Сейчас таких два: 4167 «Наушники с костной проводимостью» (1 карточка в train)
  и 6192 «Электрочайник-термос» (4 карточки). Примеров для отдельного класса мало, поэтому они входят в
  «Прочее в разделе». Карточки этих листьев обычно всё равно распознаются как наушники и чайники по соседним листьям.

### 2.6 Артефакт `models/category/`

| Файл | Размер | Содержимое |
|---|---:|---|
| `model.npz` | 6,6 МБ | веса int8 в CSR по признакам (`w_indptr`, `w_col`, `w_q`), `scale` и `bias` на класс, `idf` |
| `vocab.json.gz` | 0,9 МБ | словарь: 259 834 n-граммы трёх блоков |
| `meta.json` | 0,3 МБ | разделы, классы (id, название, путь в дереве), температуры, порог, параметры обучения |
| `metrics.json` | 45 КБ | все метрики этого документа, примеры, скорость, время обучения |

Формат без pickle: модель загружается через `np.load(..., allow_pickle=False)` и `json`. Файлы пишутся атомарно,
через временный файл и rename. Артефакт лежит в репозитории (исключение в `.gitignore`), поэтому классификатор
работает без `data/processed` и без скачивания данных. Отключить классификатор можно переменной
`CATEGORY_CLASSIFIER=off`, путь к модели задаётся через `CATEGORY_MODEL_PATH`.

## 3. Метрики на holdout

Holdout — 10% карточек по `md5(sku_id)`; сплит общий для всего проекта. Это 29 504 карточки с известной
категорией: 24 141 по офферу и 5 363 по кликам. Holdout не участвовал ни в подборе α, ни в калибровке, ни в выборе
порога и посчитан один раз. Базлайн — ветка ключевых слов `Taxonomy.classify` (последняя ступень лестницы); его копия
`category.keyword_category` сверена с оригиналом и дала 0 расхождений на 3 674 карточках. Базлайн видит полный
текст карточки, модель — заголовок и первые 300 символов описания и атрибутов продавца.

### 3.2 Лист каталога

Top-1 листа — 0,984, top-3 — 0,990, раздел каталога угадан в 0,995 случаев. Если считать только карточки, чей лист
модель различает явно, а не через «Прочее» (95,6% holdout), top-1 — 0,989. Основные путаницы — почти синонимичные
листья самого каталога:

| Истинный лист | Предсказанный лист | Карточек |
|---|---|---:|
| Подушки декоративные | Подушки | 36 |
| Подушки | Подушки декоративные | 9 |
| Шкафы для спальни | Шкафы | 8 |
| Зеркала | Зеркала для ванной | 7 |
| Блендеры | Погружные блендеры | 5 |
| Смартфоны | iPhone | 5 |

На уровне категории таксономии эти путаницы не важны: оба листа отображаются в одну категорию (`generic` или
`smartphone`). Листья с самой низкой полнотой — «Подушки декоративные» (0,66) и сборные классы «Прочее» (0,76–0,84).

### 3.3 Сегменты: справедливость и хвост

| Сегмент | Карточек | Accuracy (правила) | Accuracy (модель) | Лист top-1 |
|---|---:|---:|---:|---:|
| Категория из оффера фида | 24 141 | 0,931 | 1,000 | 0,984 |
| Категория из кликов (карточки вне фида) | 5 363 | 0,878 | 0,999 | 0,983 |
| Продавец М.Видео | 5 731 | 0,871 | 1,000 | 0,989 |
| Продавцы маркетплейса | 18 402 | 0,950 | 1,000 | 0,983 |
| Заголовок встречался в train | 7 519 | 0,948 | 1,000 | 0,999 |
| **Новый заголовок (нет в train)** | 21 985 | 0,912 | 1,000 | 0,979 |
| Лист-«голова» (≥ 1 000 карточек train) | 13 698 | 0,977 | 1,000 | 0,997 |
| Лист 100–999 карточек | 11 925 | 0,878 | 1,000 | 0,976 |
| **Хвост: < 100 карточек (в т. ч. «Прочее»)** | 3 881 | 0,857 | 0,999 | 0,961 |

- **Продавцы.** На уровне категории точность для М.Видео и продавцов маркетплейса одинаковая (1,000), на уровне
  листа — 0,989 и 0,983.
- **Дубли заголовков.** 25,5% заголовков holdout дословно встречаются в train: один товар бывает у нескольких
  продавцов. Поэтому отдельно посчитаны карточки с новыми заголовками; падает только точность листа, на 2 п. п.
- **Хвост.** На редких листьях правила теряют 12 п. п., модель — 0,1 п. п. на уровне категории и 3,6 п. п. на
  уровне листа.

## 5. Подключение к пайплайну (для интегратора)

Точка интеграции — `Taxonomy.classify(card)` в `src/attrx/taxonomy.py` (`detect_category` — обёртка для
совместимости, возвращает `(категория, уверенность)`). Классификатор работает, когда более надёжные ступени лестницы
не сработали: `category_id` из таксономии или известный лист каталога вне неё (→ `generic`, уверенность 1,0), точное
название категории в `card.category`, внешний хук `set_category_hook`. Модель загружается лениво — при первой такой
карточке (`Taxonomy.classifier()`); `category.py` не импортирует `taxonomy.py`, поэтому цикла импортов нет:

```python
from attrx.category import CategoryClassifier, CategoryPrediction

clf = CategoryClassifier.load(taxonomy=tax)   # один раз; None — нет артефакта / CATEGORY_CLASSIFIER=off / битый файл
if clf is not None:
    p: CategoryPrediction = clf.predict(card)  # Card или dict {title, description, seller_attrs}
    # card.title = "Чехол для iPhone 16 Pro силиконовый, прозрачный"
    p.leaf_id, p.leaf_title                    # "1189", "Чехлы для смартфонов" (или "other:<id раздела>")
    p.taxonomy_category, p.confidence          # "generic", 0.9999 — калиброванная P(категория | текст)
    p.top3                                     # [("1189", "Чехлы для смартфонов", 0.9907), ("other:56077", …), …]
    clf.leaf_path(p.leaf_id)                   # ["Аксессуары для телефонов", "Чехлы для телефонов", "Чехлы для смартфонов"]
    clf.is_review(p)                           # False: p.confidence ≥ clf.threshold (0.9)
    clf.predict_many(cards)                    # пакет: 1 400–1 900 карточек/с на ядро
```

Как использовать результат:

- **Решение.** `classify` возвращает `CategoryDecision(name, confidence, source="classifier", title, path, review)`:
  `name` — `p.taxonomy_category` (категория вне таксономии → `generic`), `confidence` — `p.confidence`,
  `title = p.leaf_title`, `path = clf.leaf_path(p.leaf_id)`, `review = clf.is_review(p)`. В `ExtractionResult` они
  попадают в `category`, `category_confidence`, `category_title` и `category_path`.
- **Ниже порога** (`review = True`). Категория остаётся лучшей гипотезой модели, все значения карточки со статусом
  `accepted` становятся `review` (`pipeline.Extractor.extract`), а в `warnings` добавляется
  «категория определена неуверенно (classifier: <лист>, 0.42) — карточка на проверку». Карточка уходит в очередь
  модератора. Правку категории как новую обучающую метку обратная связь пока не пишет (сейчас — только правки
  атрибутов) — это план.
- **Отображение и правка таксономии.** `CategoryPrediction` — это `NamedTuple` с пятью полями, его можно
  распаковать как кортеж. Если таксономия поменялась на лету, вызывается `clf.set_taxonomy(tax)`; диагностика —
  `clf.info()`: классы, порог, временное отображение, листья вне пространства меток.

## 6. Воспроизведение

```bash
uv pip install -p .venv/bin/python -e ".[ml]"   # для обучения нужен scikit-learn (инференсу хватает numpy)
.venv/bin/attrx prepare                          # data/raw -> data/processed (см. .claude/context/DATA.md)
.venv/bin/attrx train-category                   # обучение + метрики -> models/category (~6 мин)
.venv/bin/attrx train-category --search          # + подбор α на dev по сетке 2e-6 / 5e-6 / 1e-5 (~10 мин)
.venv/bin/pytest -q tests/test_category.py
```

| Этап | `attrx train-category` | `attrx train-category --search` |
|---|---:|---:|
| загрузка карточек (DuckDB) | 16 с | 17 с |
| словарь и признаки (2 процесса) | 57 с | 29 с |
| обучение двух этапов + калибровка на dev | 258 с (одно α) | 481 с (три α) |
| holdout (модель и правила) | 25 с | 27 с |
| cold start: 20 тыс. карточек и замер скорости | 17 с | 22 с |
| **итого** | **376 с, пик памяти 4,1 ГБ** | **578 с, пик памяти 4,8 ГБ** |

Замеры сделаны на 4 ядрах с `n_jobs=2`. Машину одновременно использовали другие процессы, поэтому время этапов
от прогона к прогону различается до двух раз. Правая колонка взята из `metrics.json` → `timings_s`, левая — из
повторного прогона без `--search`. Прогон детерминирован: фиксированный seed, сплиты по `md5(sku_id)`, словарь по
выборке с seed. Повторный запуск без `--search` выбирает то же α = 2e-6 по умолчанию и даёт побитово тот же
артефакт (веса, словарь, `meta.json`) и те же метрики. Тесты (`tests/test_category.py`) от `data/processed` не зависят:

- признаки и нормализация блоков;
- отображение на таксономию, включая временное;
- пространство меток;
- инференс на модели, собранной вручную, без scikit-learn;
- загрузка: нет артефакта, `CATEGORY_CLASSIFIER=off`, битый `meta.json`;
- метрики и порог;
- сквозное обучение на синтетическом мини-каталоге во временной папке;
- smoke-тест настоящего артефакта (выполняется, только если артефакт есть).

## 7. Ограничения и риски

- **Эталон категории неидеален.** Для карточек вне фида категория взята из кликов (`seo_id`). Он совпадает с
  категорией оффера в 97,7% случаев: товар бывает кросс-листингом в соседний лист. В самом каталоге есть почти
  синонимичные листья («Подушки» и «Подушки декоративные»). Поэтому точность листа (0,984) — нижняя оценка.
- **Сдвиг распределения на cold start.** Без категории много товаров, которых почти нет в фиде: инструменты,
  мототовары, продавцы GSS/UNIMALL с заголовками вида «Робот GSS -». Такие карточки модель относит к ближайшему
  известному листу. Категория при этом почти всегда `generic`, и это безопасно: извлекаются общие атрибуты. Лист
  может быть неточным, как пример 10 в разделе 4. Для `generic` уверенность высока по построению — это сумма
  сотен листьев. Поэтому в UI отдельно показывается вероятность листа.
- **Нет эталона для cold start.** Согласие с правилами — не точность. Проверка глазами на 15 карточках
  показательна, но статистически мала. Следующий шаг — gold-сет из карточек модерации.
- **Редкие и новые листья.** Листья с числом карточек в train меньше 10 не выделены в отдельный класс; сейчас из
  таксономии это 4167 и 6192. Новые листья каталога требуют переобучения: это одна команда на ~6 мин, её можно
  запускать ежемесячно или при появлении новых листьев.
- **Границы таксономии.** Пять из семи ошибок на holdout вызваны листьями-соседями категорий, которых нет
  в `category_ids` (раздел 3.5). Это решение владельца таксономии.
- **Линейная модель на мешке n-грамм.** Порядок слов дальше биграмм модель не учитывает. Ситуацию «аксессуар для X»
  ловят биграммы («для ноутбука»), но сложные заголовки без типа товара («Демо КБТ HAIER …») уходят в ошибку или
  на проверку.
- **Мониторинг дрейфа.** Нужно следить за долей карточек ниже порога и за распределением предсказанных категорий;
  то и другое считается в `metrics.json` → `unlabeled`. Рост доли «Прочее» или карточек ниже порога — сигнал
  переобучить модель.
