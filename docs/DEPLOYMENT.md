# Внедрение в М.Видео

Как attrx встаёт в контур М.Видео: без VPN, с LLM внутри периметра, через батч и API, с раскаткой по гейтам и петлёй
обратной связи. Статус: **есть** — работает в репозитории; **план** — будет сделано, указан срок. Продуктовые цели и
KPI — [PRD.md](PRD.md), риски — [RISKS.md](RISKS.md).

## Коротко

- Один Docker-контейнер (Python 3.11, CPU): правила + словари + классификатор категории, API и интерфейс модератора.
  NER — при установке extra `[ml]` и обученной модели `models/ner` (в базовый образ не входят); LLM — отдельный сервис
  в контуре.
- Без LLM решение полностью рабочее: режим без LLM — штатный, а не аварийный.
- Интеграция с PIM — пакетно (CLI по выгрузке) или онлайн (REST API); результат — канон, уверенность, статус, цитата.
- В каталог сразу ничего не пишем: офлайн-гейт → тень → автопринятие выше порога → масштаб, с откатом категории в тень.

## 1. Схема в контуре

```
PIM / контент-система
   │  выгрузка карточек (title, description, атрибуты продавца)
   ▼
attrx extract (батч)  или  attrx API :8000 (/api/extract, /api/extract/batch)
   │  категория → правила и словари → NER → LLM только для хвоста → заземление → калибровка → статус
   │                                     │
   │                          OpenAI-совместимый endpoint в контуре (vLLM / Ollama)
   ▼
predictions.jsonl / .csv
   ├─ accepted ─────────► запись в PIM
   ├─ review ───────────► очередь модерации (UI attrx или существующий инструмент) ─► /api/feedback
   └─ missing ──────────► отчёт «нет в тексте» → запрос продавцу                        │
                                                                                         ▼
                                                     feedback.jsonl → attrx learn → словари (следующий прогон)
```

## 2. LLM: где живёт модель

| Режим | Как включить | Где данные | Когда |
|---|---|---|---|
| Без LLM: правила, словари, классификатор категории (+ NER при `[ml]` и `models/ner`) | `LLM_ENABLED=false` | не покидают сервер | старт, закрытый контур, отказ LLM |
| On-prem LLM | vLLM или Ollama на GPU-сервере: `LLM_BASE_URL=http://<gpu-сервер>:8000/v1`, `LLM_MODEL=Qwen/Qwen2.5-7B-Instruct` (пример) | в контуре М.Видео | целевой прод |
| Российские облака | GigaChat (через прокси gpt2giga), YandexGPT — оба OpenAI-совместимые | наружу уходит только текст карточки, без персональных данных | пилот без своих GPU |
| Ключ организаторов | `OPENAI_API_KEY` / `OPENAI_BASE_URL` на ВМ подхватываются при `LLM_ENABLED=auto` | шлюз хакатона | только демо и замеры |

VPN и прокси не нужны: все варианты доступны из РФ, провайдер меняется переменными `.env`, код не трогаем.
Локальный вариант собран в `docker-compose.yml`: `docker compose --profile llm up` поднимает Ollama рядом с приложением. **есть**

Сравнение моделей по латентности, валидности JSON, заземлению и цене — `attrx llm-bench` на реальных карточках;
тарифы — `config/llm_prices.yaml`, расчёт «₽ на 1000 карточек» — `src/attrx/llm/cost.py`. **есть**. Замер на holdout
(`submission/cost.json`, [LLM.md](LLM.md) §6): LLM зовётся для 31% карточек, 969 + 52 токена и 3,3 с на вызов
(qwen3:4b-instruct, GTX 1060). За 1000 карточек гибрид — 0,83 ₽ на своей GPU, 20,6 ₽ через GigaChat Lite, 63,2 ₽ через
YandexGPT Lite против 5,6 / 84,6 / 260,2 ₽ у «LLM на каждую карточку»; прод-сервер с L4 и vLLM — оценка ≈ 3,6 ₽ гибрид
и ≈ 11,5 ₽ «на каждую». Качество на 4B-модели: значения одной LLM верны в 38% случаев, поэтому в проде LLM —
подсказки модератору; перед раскаткой — тот же замер на целевой модели.

## 3. Интеграция

| Канал | Что | Статус |
|---|---|---|
| Батч | `attrx extract -i <выгрузка> ` → `predictions.jsonl` и `.csv`: на каждый атрибут канон, единица, уверенность, статус, источники, цитата | есть |
| API | `POST /api/extract` (карточка), `POST /api/extract/batch` (до 1000), `GET /api/review/queue` (очередь по приоритету «вес спроса × (1 − уверенность)»), `POST /api/feedback`, `POST /api/feedback/undo`, `GET /api/health`; Swagger — `/docs` | есть |
| Конфигурация | категории, обязательные атрибуты, словари, пороги — `config/*.yaml` и `.env`; в compose смонтированы `./config`, `./data`, `./outputs` | есть |
| Повторяемость | ответы LLM кэшируются по хэшу запроса: повторный прогон воспроизводим и бесплатен | есть |
| Асинхронный хвост | в проде LLM обрабатывает хвост в фоне, карточка публикуется с уже принятыми значениями | план |

Контракт выхода — [PRD.md](PRD.md), раздел 8.

## 4. Раскатка

| Этап | Что делаем | Гейт перехода | Откат |
|---|---|---|---|
| 0. Офлайн | метрики на holdout, разбор ошибок по атрибутам и сегментам | precision автопринятого ≥ 0,95; разрыв F1 по продавцам ≤ 5 п.п., по размеру категории ≤ 10 п.п. — **выполнено**: 0,954; 2,0 и 5,2 п.п. (весь holdout, 23 391 карточка) | — |
| 1. Тень, 2–4 недели | предсказания пишутся рядом, не в каталог; сверяются с решениями модераторов; отдельный аудит слоя уверенности 0,70–0,80 (на holdout он верен лишь на 57%) и решение о калибровке на всём dev (кандидат: порог 0,82); порог по категориям | precision на выборочном аудите ≥ 0,95, в том числе у порога | — |
| 2. Автопринятие | `accepted` → PIM в топ-категориях по трафику, `review` → очередь; ежедневный выборочный аудит | стабильная precision 2 недели | precision ниже гейта → категория обратно в тень |
| 3. Масштаб | все категории; холодный старт через LLM со статусом `review`; NER дообучается на правках | — | тот же порог по категории |

## 5. Мощности и скорость

- Весь корпус в 1,18 млн описаний — офлайн-батчем. Весь holdout, медиана 3 замеров: правила — 1 516 карточек/с на одно
  ядро (корпус ~13 мин), с NER на GPU — 421 карточка/с (~45–50 мин); классификатор категории — ~1 мс на карточку, 8–10 мин
  на 880 тыс. карточек без категории ([CATEGORY.md](CATEGORY.md)); NER на CPU без AVX — ~60 мс на карточку
  ([NER.md](NER.md)). Цель — p95 ≤ 50 мс на карточку без LLM на сервере с GPU или CPU с AVX; среднее на holdout —
  2,4 мс с NER, p95 отдельно не мерили (план).
- LLM — только хвост. Параллелизм — `LLM_CONCURRENCY`, ограничение входа — `LLM_MAX_INPUT_CHARS`, лимиты —
  `LLM_MAX_CALLS` и `LLM_DAILY_MAX_CALLS`. **есть**
- Экономика: стоимость гибрида ≈ p_LLM × стоимость «LLM на каждую карточку»; on-prem — амортизация GPU плюс
  электричество, делённые на пропускную способность (`src/attrx/llm/cost.py`).

## 6. Мониторинг и дрейф

| Сигнал | Откуда | Статус |
|---|---|---|
| Версия, пороги, включены ли LLM и NER | `GET /api/health` | есть |
| Доступность LLM-сервера, задержка, состояние предохранителя, вызовы за сутки | `attrx llm-status` | есть |
| Вызовы LLM, токены, попадания в кэш, латентность | `client.stats()` в `src/attrx/llm/client.py` | есть |
| На карточку: время этапов, отброшенные значения LLM, «кандидаты в справочник», конфликты, неуверенная категория | поля `timings_ms` и `warnings` результата | есть |
| Калибровка: точность принятых при пороге, ECE, худшая ячейка «категория / атрибут / источники» | `attrx calibrate` → `config/calibration.json`; на holdout — `submission/calibration.json` | есть: обучена на продавце, правилах и NER (порог 0,70; на всём holdout ECE 0,019, но слой у порога 0,70–0,80 верен лишь на 57% — [EVALUATION.md](EVALUATION.md) §9.5); с LLM — план |
| По категориям: доля `review` и `missing`, средняя уверенность, конфликты, неуверенная категория, доля вызовов LLM и отброшенных значений — против эталонного прогона, алерт с действием | `attrx monitor` (`src/attrx/monitor.py`, [MONITORING.md](MONITORING.md)); `--fail-on-alert` для cron | есть |
| Precision выборочного аудита принятого, в том числе слоя уверенности 0,70–0,80 | журнал решений модератора (`feedback`) | план (пилот) |
| Признаки дрейфа: сдвиг распределения категорий (PSI, JS), новые листья каталога, рост доли generic; значения LLM вне справочника, новые ключи продавцов без алиаса | `attrx monitor`; заметки LLM-экстрактора | есть (монитор) / план (ключи продавцов) |

Реакция на дрейф: категория возвращается в тень, ключи и значения из заметок становятся кандидатами в словари,
словари каталога пересобираются (`attrx build-dicts`), калибровка — `attrx calibrate`, классификатор категории —
`attrx train-category` (~6 мин на CPU) при появлении новых листьев, NER дообучается на накопленных правках (план).

## 7. Петля обратной связи

1. Модератор подтверждает или исправляет значение в очереди → `POST /api/feedback` → `outputs/feedback.jsonl`. **есть**
2. `attrx learn` превращает исправленные формулировки в синонимы `config/dictionaries/learned.yaml`; словари лежат в git,
   любое изменение можно откатить. **есть**
3. Правки становятся эталоном для метрик и обучающими примерами для NER; очередь сортируется так, чтобы человек
   размечал самое ценное: вес спроса × неуверенность. Сортировка — **есть**, правки в эталон и NER — **план**.

## 8. Эксплуатация и безопасность

- Ключи — только в `.env` и переменных окружения, в git не попадают.
- Модель не пишет HTML и JS для интерфейса: экран собирается из фиксированного набора компонентов по схеме
  (`src/attrx/genui/`), значения берутся из результата пайплайна ([GENUI.md](GENUI.md)).
- В логах и предупреждениях — только данные карточек товаров, персональных данных нет.

## 9. Запуск на ВМ хакатона (демо на порту 8000)

```bash
uv venv -p 3.11 .venv && uv pip install -p .venv/bin/python -e ".[dev]"
.venv/bin/attrx serve --host 0.0.0.0 --port 8000   # = make serve-public; LLM подхватит OPENAI_API_KEY / OPENAI_BASE_URL с ВМ
# или
docker compose up -d --build     # то же в контейнере: правила + словари + классификатор категории (NER — с [ml] и models/ner)
```
