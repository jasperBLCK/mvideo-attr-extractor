# Протокол оценки

Как мы меряем качество извлечения характеристик на **реальном каталоге М.Видео**: что считается эталоном, как он
строится, как сравниваются значения, какие метрики и разрезы считаются и какие у оценки ограничения.
Код: `src/attrx/eval/gold.py` (эталон), `src/attrx/eval/metrics.py` (метрики), `src/attrx/eval/real.py` (прогон);
тесты правил сравнения — `tests/test_eval_gold.py`.

```bash
attrx prepare          # data/raw -> data/processed/*.parquet (поток данных, см. docs/EDA.md)
attrx build-gold       # эталон -> data/processed/gold.parquet, gold_dev.jsonl, gold_holdout.jsonl, data/sample/real_gold.jsonl
attrx eval-real        # базовая линия: продавец + правила на dev -> data/processed/baseline_dev.json + таблица
attrx eval-real --sources seller,rules,ml,llm --out data/processed/hybrid_dev.json   # любой набор шагов гибрида
```

## 1. Эталон: что это и почему ему можно доверять

**Эталон — характеристики товара в YML-фиде М.Видео** (`skus.pkl`): `vendor` (бренд), `model` (модель) и `param[]`
(характеристики). Их заполняет и проверяет контент-команда маркетплейса, по ним работают фильтры и поиск сайта —
это ровно та «человеческая» разметка по категориям, которую кейс просит использовать как gold-сет, только не на
20 карточках, а на **241 355 карточках** (все SKU из `sku_desc` с оффером в фиде).

**Что получает пайплайн (и чего нет):** текст карточки из `sku_desc` (название + очищенное описание + блок
«Характеристики:» продавца, `Card.full_text()`) и **id категории каталога** (`category_id`, у карточек с оффером — из
фида, как у карточки в листинге каталога; название категории — запасной путь, если id нет). Характеристики фида
(`vendor`, `model`, `param`) — эталон — в пайплайн не подаются. Имя продавца передаётся в `Card.seller`, но в извлечении
не участвует (только разрезы справедливости). Без `category_id` категорию выбирает классификатор по тексту
(`attrx.category`); на holdout это измерено отдельным прогоном (§9).

Эталон строится одинаково для всех карточек (`attrx build-gold`, 2–3 мин, ~1 ГБ RAM):

1. **Категория.** `config/taxonomy.yaml` сопоставляет категориям таксономии листья дерева YML (`category_ids`):
   смартфоны = «Смартфоны» (761) + «iPhone» (914), ноутбуки = 987, стиральные машины = 2447 + 2451 + 501 и т.д.
   Карточки прочих категорий получают схему `generic` (бренд, модель, цвет) — это длинный хвост и cold start.
2. **Источник значения.** У каждого атрибута в таксономии есть `gold:` — `vendor`, `model` или имена параметров фида
   по приоритету. У параметра бывает пара «бакет фильтра» и «точное значение» (`<имя>_search`, с `@unit`):
   `Диагональ экрана = 6.6" и более` и `Диагональ_search = 6.7 ["]`. **Берём точный вариант**; бакет — только если
   точного нет **и** бакет не диапазон (`от 15 до 16.9`, `3000-5000 мАч`, `до 2 л`, `6.6" и более` отбрасываются:
   угадывать точное значение по диапазону нельзя). Категориальные бакеты (`True Wireless`, `узкая`) допустимы.
3. **Нормализация — тем же кодом, что и предсказания** (`normalize.py`), см. раздел 3.
4. **Бренд не указан — не эталон.** Заглушки `vendor` («нет бренда», «No Name», «###»; ~2,5% карточек хвоста)
   означают «бренда нет», поэтому эталоном бренда не считаются (предсказание там — `new_fill`, а не ошибка):
   `dictgen.is_placeholder`, правило применяется и при сборке эталона, и в `metrics.match_key`.
5. **Несколько допустимых значений.** Если фид честно допускает несколько ответов, эталон хранит список:
   многоцветный товар (`черный/ серебристый` -> `[чёрный, серебристый]`); модель — `model` оффера плюс «конкретные»
   (с цифрой) варианты из параметров `Серия`/`Модель` (`A36`, `Galaxy A36`, `SM-A366`); процессор — полная модель
   и семейство (`Intel Core i5-12450H`, `Intel Core i5`). Предсказание верно, если совпадает с любым из них.
6. **Извлекаемость** (`extractable`): есть ли эталонное значение в тексте карточки в любом распознаваемом написании —
   число с единицей (`256 ГБ` ~ `256GB` ~ `12/256`, `1024 ГБ` ~ `1 ТБ`, `6.7` ~ `6,7"`), «узнаваемое» голое число
   (дробное или ≥ 100: `6.67`, `5 000`), синоним из справочника (`чёрный` ~ `Black`, `Midnight`), бренд/модель как
   слово (без пробелов и дефисов). Это **потолок для извлечения только из текста**: если значения в тексте нет,
   его не извлечёт никакой метод без «выдумывания», а выдумывать кейс запрещает.

Файлы (в git не попадают, кроме сэмпла):

| Файл | Содержимое |
|---|---|
| `data/processed/gold.parquet` | строка на (карточка, атрибут): `sku_id, split, category, category_id, attribute, value` (канон), `value_num`, `alternatives` (JSON-список допустимых), `raw_value, raw_unit, unit, source` (откуда взято), `mapped` (сопоставилось со справочником), `extractable`, сегменты `seller_type, size_band, desc_band` |
| `data/processed/gold_{dev,holdout}.jsonl` | `{"id", "category", "split", "attributes": {attr: значение \| [допустимые]}, "extractable": {...}, сегменты}` — формат `io.load_gold` |
| `data/sample/real_gold.jsonl` | то же для 400 закоммиченных реальных карточек `data/sample/real_cards.jsonl` (демо и тесты без датасета) |

## 2. Сплиты

Детерминированно по `md5(sku_id) % 100`: train 80% / dev 10% / holdout 10% (`attrx.data.split_of`).
Карточек с эталоном: train 193 306 / dev 23 906 / holdout 24 143; в категориях таксономии — 13 090 / 1 532 / 1 650.

- **dev** — настройка правил, словарей и порогов и сравнение шагов гибрида (все числа в этом документе — dev);
- **holdout не трогаем** до финального отчёта: правила и словари на нём не смотрим, пороги на нём не подбираем;
- train — для обучения NER (distant supervision) и самообучающихся словарей/алиасов.

Карточек с эталоном мало у отдельных категорий (holdout: смартфоны 441, ноутбуки 122), поэтому в отчётах всегда
указывается `n_gold` по каждой ячейке «категория × атрибут».

## 3. Правила сравнения

Эталон и предсказание приводятся к ключу одной функцией `metrics.match_key` (нормализаторы из `normalize.py`):

| Тип | Ключ | Пример |
|---|---|---|
| число | значение в канонической единице атрибута; совпадение с **относительным допуском 1%** | `1 ТБ` = 1024 ГБ; `6.7"` ~ `6.67"`; `30 мин` = 0.5 ч; `450 мм` = 45 см |
| цвет | первая базовая из 17 цветов палитры `config/dictionaries/colors.yaml` | `Midnight`, `черный матовый`, `графитовый` -> `чёрный`; `голубой` -> `синий` |
| справочник (enum) | канон справочника; если значение в справочник не попало — само значение | `NoFrost`, `Total No Frost` -> `No Frost`; `TWS` -> `True Wireless` |
| бренд | канон справочника брендов или `vendor` как есть | `Самсунг` = `Samsung`; регистр не важен |
| модель | `model_core`: без бренда, слова категории, памяти, цвета, диагонали, скобок, `5G/LTE/Dual Sim/eSim`; затем без регистра, пробелов, дефисов и пунктуации (`+` -> `plus`) | `Galaxy S25 5G 12/128GB Серый` = `galaxys25`; `S24+` ≠ `S24` |
| процессор | без производителя, частот, «Core», повторов: `Intel Core i5 12450H 2.0 ГГц` = `i5-12450H`; если в эталоне только семейство (`Core i5`), засчитывается любая модель этого семейства | `M4 Pro` ≠ `M4` |
| да/нет | `да`/`нет` (`Да`, `есть`, `отсутствует`, …) | |
| строка | без регистра, ё/е, пробелов, дефисов и пунктуации | |

Эталон-список: предсказание верно, если совпало с **любым** допустимым значением.

## 4. Метрики

Каталожный эталон **неполный**: у товара может быть не заполнена характеристика, которая есть в тексте. Поэтому
предсказание там, где эталона нет, **не считается ошибкой** — это кандидат на дозаполнение каталога.

Для каждой пары (карточка, атрибут), где пайплайн выдал значение со статусом `accepted` (или выше порога в `threshold_sweep`):

| Метрика | Определение |
|---|---|
| `tp` / `fp` / `fn` | только на парах, **где эталон есть**: верное значение / неверное значение / эталон есть, а верного значения нет (`fn = n_gold − tp`) |
| **Precision, Recall, F1** | `tp/(tp+fp)`, `tp/n_gold`, гармоническое среднее — по каждому атрибуту, по ячейке «категория × атрибут», micro по всем |
| **`new_fills`** | значения там, где в каталоге пусто (не FP): на сколько слотов каталог может стать полнее |
| **`recall_extractable`** | recall только на эталонных значениях, которые есть в тексте карточки — качество метода без учёта недостижимого |
| `extractable_share` | доля эталонных значений, которые вообще есть в тексте (потолок recall для «только текст») |
| **Покрытие** | `catalog_fill` — доля карточек, где атрибут заполнен в каталоге; `pred_fill` (= `coverage`) — где его заполнил пайплайн; `union_fill` — где он есть после дозаполнения (`(n_gold + new_fills)/n`): «насколько полнее становится каталог» |
| **Traffic-weighted F1/P/R** | `Σ W(c,a)·F1(c,a) / Σ W(c,a)` по ячейкам с эталоном; `W(c,a)` = доля поисковых кликов категории × вес атрибута по спросу внутри категории (`config/traffic_weights.yaml` из `query_clicks`, `attrx traffic`; для `generic` — средний по кликам вес атрибута в категориях вне таксономии; без файла — `traffic_weight` из таксономии) |
| macro-F1 | среднее F1 по атрибутам (`macro_f1`) и по ячейкам (`macro_f1_cells`) — редкие атрибуты весят наравне с частыми |
| `review_rate` | доля слотов со статусом «на проверку» (нагрузка на модераторов) |
| `threshold_sweep` | precision / recall / coverage / new_fills при пороге уверенности 0…1 — выбор порога под целевую точность |

Общая accuracy не используется: она маскирует провалы на хвосте (требование кейса).

## 5. Справедливость: разрезы

Все метрики пересчитываются по сегментам (`segments` в отчёте; `metrics.segment_metrics`):

| Сегмент | Значения | Зачем |
|---|---|---|
| `seller_type` | `mvideo` (собственные карточки М.Видео), `marketplace` (партнёры), `none` | мелкие продавцы не должны страдать |
| `size_band` | `head` (листовая категория ≥ 1000 офферов), `torso` (100–999), `tail` (< 100) | редкие категории — длинный хвост |
| `desc_band` | `short` (< 500 символов описания), `medium` (500–1499), `long` (≥ 1500) | бедные карточки (квартили описаний с эталоном: 25% — 644, медиана — 1004) |
| `category` | 12 категорий таксономии + `generic` | качество по категориям, а не в среднем |

Выборка `eval-real`: все карточки dev с эталоном в категориях таксономии (их 1 532, поэтому «5 000» не набирается)
+ 1 000 карточек `generic`, стратифицированных по `size_band` (пропорционально, но не меньше 150 на полосу), seed 0.

## 6. Известные ограничения оценки (и что с ними делаем)

- **Эталон неполный** -> предсказания без эталона считаем `new_fills`, а не ошибками; их точность оцениваем
  выборочной ручной проверкой (очередь модерации), а не автоматически.
- **Эталон иногда ошибается** (мусорные `model` вида «Телевизор смарт», «Чайник электрический 1.7 л»; маркетинговые
  названия цветов). Модели без латиницы и цифр эталоном не считаются; цвета сведены к базовой палитре.
- **Значения нет в тексте** (iPhone: ёмкость батареи почти не указывается; холодильники: высота, число камер) —
  поэтому всегда показываем `recall_extractable` и `extractable_share` рядом с recall.
- **Бакеты фильтров** — не точные значения; диапазоны не используем, точный вариант `_search` в приоритете.
- **Справочники влияют на сравнение** (цвет «бирюзовый» ≠ «синий»): одна и та же нормализация применяется к эталону
  и предсказанию; несопоставленные со справочником значения эталона помечены `mapped = false` — это список пробелов
  справочников для следующей итерации, а не ошибки модели.
- **Мало эталонных карточек** в отдельных ячейках (dev: десятки–сотни) — в отчёте всегда `n_gold`;
  для смартфонов/ноутбуков финальные цифры — на holdout.
- **Блок «Характеристики» продавца** у карточек с эталоном редок (6,6%) — оценка в основном меряет извлечение из
  названия и описания; эффект атрибутов продавца на хвосте каталога (37,5% карточек без оффера) оцениваем отдельно.

### 8.3 Калибровка уверенности и порог автопринятия

`attrx calibrate` (только dev) → `config/calibration.json`; применяется в `Extractor` (`confidence.Calibrator`).

- **Что калибруется:** сырая оценка агрегатора (noisy-OR источников, минус половина поддержки альтернативы) →
  P(значение верно). Группы — от частной к общей: «категория/атрибут/источники[/конфликт]» → «источники|тип
  атрибута[|конфликт]» → «*|тип» (тип: бренд, модель, цвет, справочник, число, процессор). Кривая — изотоническая
  регрессия (PAV), блоки сглажены к точности родительской группы; группа с 25–79 точками получает форму
  родительской кривой, масштабированную к своей (сглаженной) точности — иначе маленькая слабая ячейка
  наследовала бы оптимистичную общую кривую. 78 кривых.
- **Порог:** наименьший, при котором на 2-fold кросс-фиттинге по карточкам dev (кривые учатся на одной половине,
  применяются к другой) нижняя граница 95% ДИ Уилсона точности принятых ≥ 0,95 **и** ни в одной ячейке с ≥ 20
  принятыми точность не ниже 0,75. Второе условие — против «среднее маскирует хвост»: при одном общем критерии
  порог 0,50 принимал бы время работы наушников с точностью 0,38.
- **Итог: порог 0,70** (калибровка обучена на продавце, правилах и NER после исправлений v2: 9 294 значения dev,
  88 кривых; до v2 тем же правилом выходил порог 0,69). На отложенных половинах: точность принятых **0,967** (нижняя
  граница 0,963) при покрытии **0,935** (доля предсказанных значений с эталоном, которые принимаются); худшая ячейка —
  время работы пылесоса (0,75); ECE 0,012. Без калибровки при том же пороге — 0,960 / 0,933.
- Теперь уверенность значит то, что написано: на dev точность принятых растёт с порогом 0,942 (0) → 0,968 (0,7)
  → 0,987 (0,9) → 0,990 (0,95) (`threshold_sweep` в `rules_dev.json`); в базовой линии порог почти не управлял
  точностью: 0,885 (0) → 0,897 (0,7) → 0,913 (0,9).
- **Согласие не понижает уверенность.** Для сочетания источников без своей кривой (например, «правила + LLM»)
  уверенность — максимум из общей кривой типа и калиброванной уверенности того же значения без добавленного
  источника (`Calibrator.monotone`): подтверждение LLM или NER может только поднять уверенность. Согласные источники
  не считаются конфликтом и тогда, когда записали значение по-разному (модель «Redmi Note 13» и «Redmi Note 13
  8/256GB» сравниваются ключом метрик).

| Точность принятых | 0,953 | 0,959 | 0,962 | **0,967** | 0,974 | 0,982 | 0,987 |

### 9.4 Срезы: новые названия и без `category_id`

выбор схемы атрибутов; точность до листа каталога — docs/CATEGORY.md.

### 9.5 Калибровка у порога — слабое место (раскрываем как есть)

- **Найдено ревьюером на holdout v1:** на стратифицированном наборе в бине уверенности 0,7–0,8 обещано 0,745, верных
  0,648 (n = 287). **В v2 на тех же карточках — 0,745 против 0,652 (n = 276)**; точность принятых значений с
  уверенностью в [0,70; 0,80) — 0,648 (n = 273, 3,4% принятых).
- **На всём holdout v2 слабость больше:** точность принятых в [0,70; 0,80) — **0,569** при средней уверенности 0,751,
  n = 2 008. Это 4,1% принятых, но 865 из 2 270 неверных принятых (38%). 91% слоя — две ячейки хвоста: цвет (1 050
  значений, верны 0,553) и модель (746, верны 0,546).
- **Остальная шкала держится:** ECE 0,019 на всём holdout (0,012 на стратифицированном); в бине 0,9–1,0 (43 704
  значения — 84% всех) верных 0,982 при средней уверенности 0,990.
- **На dev та же картина — это не случайность holdout:** точность принятых в [0,70; 0,80) на стратифицированном dev
  (на нём калибровка и учится) — 0,657 (n = 286), на всём dev (23 554 карточки) — 0,581 (n = 2 034), из них 1 792 —
  цвет и модель хвоста.
- **Причина:** калибровка учится на стратифицированном dev — все 1 531 карточка таксономии и только 1 050 карточек
  хвоста. У ячеек хвоста мало точек около порога, их кривые сглажены к родительским группам, а родитель оптимистичен
  для хвоста. В каталоге же хвост — 94% карточек.
- **Кандидат на исправление (замерен только на dev, в v2 не применён):** калибровать на всех карточках dev (52 848
  значений вместо 9 294, 108 кривых). На кросс-фиттинге по всему dev: ECE 0,003, точность принятых в [0,70; 0,80) —
  0,756 (n = 1 569). На всём dev сейчас: точность принятых 0,955 при доле принятых 0,940; с новой калибровкой при том
  же пороге 0,70 — 0,970 / 0,905, а то же правило выбора выдаёт порог 0,82 — 0,982 / 0,855. Цена — 8–9% найденных
  значений уходят модератору вместо автопринятия. Решение о переходе — по мониторингу на новых данных
  (docs/MONITORING.md), а не по этому holdout.
