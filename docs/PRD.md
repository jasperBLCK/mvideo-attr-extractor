## 1. Проблема

Характеристика товара — это фильтр, выдача по атрибутному запросу, признак для рекомендаций и ключ склейки одинаковых
SKU. Цепочка из брифа М.Видео: характеристика заполнена → товар в фильтрах → выше CTR и конверсия → рост GMV.
Обратная цепочка — прямые потери: пустая характеристика выводит товар из фильтра и атрибутной выдачи.

Что показывают данные кейса (`.claude/context/DATA.md`, [EDA.md](EDA.md), [checkpoint/demand_stats.json](checkpoint/demand_stats.json)):

| Факт | Значение |
|---|---|
| Описаний карточек (вход) | 1 177 200 |
| Офферов каталога со структурированными характеристиками (эталон) | 546 069 в 6 963 категориях |
| Кликов из поиска | 30 991 350, уникальных запросов 1 397 078 |
| Клики по запросам, где покупатель назвал атрибут | **56,5 %**; характеристику кроме бренда и модели — **24,9 %** (оценка снизу, [EDA.md](EDA.md) §6) |
| Примеры: «игровые ноутбуки» · «встраиваемые посудомоечные машины 45см» · «телевизоры 55» | 88 336 · 75 371 · 61 792 клика |
| Карточек без оффера в фиде и без кликов — есть только текст | 880 632 (75 %) |
| Карточки с эталоном: партнёры маркетплейса / М.Видео | 77 % / 23 % (241 355 карточек) |
| Блок «Характеристики» от продавца у карточек с эталоном | 6,6 % — опираться на поля продавца нельзя |
| Эталонное значение есть в тексте карточки | 83 % значений на всём holdout (79 % на стратифицированном наборе); смартфоны: диагональ 34–51 %, батарея 50 % |

Выводы для продукта:
1. Покупатели ищут характеристиками — заполненность фильтров напрямую конвертируется в спрос.
2. Основной источник — свободный текст: структурированных полей продавца почти нет, а у 75 % карточек нет и категории.
3. Текст не содержит всех значений. Решение обязано честно говорить «в тексте нет», а не додумывать —
   иначе LLM «вспомнит» диагональ по названию модели и испортит фильтр.

## 2. Цель, границы и не-цели

**Цель.** Автоматически заполнять обязательные характеристики из текста карточки так, чтобы в каталог попадали только
надёжные значения (precision ≥ 0,95), а сомнительные уходили модератору с цитатой; при этом платить за LLM только
там, где без неё не обойтись.

**В границах:**
- вход — только текст карточки: название, описание, атрибуты продавца;
- категория карточки по тексту, если её нет (классификатор);
- 12 категорий таксономии (смартфоны = листья 761 + 914, ноутбуки = 987, телевизоры, стиральные машины, холодильники
  и др.) и `generic` (бренд, модель, цвет) для остального каталога;
- извлечение, нормализация к канону, калиброванная уверенность, статус, цитата;
- очередь модерации и петля обратной связи в словари;
- API, батч-CLI, интерфейс модератора, офлайн-оценка и отчёт.

**Не-цели:**
- изображения (в кейсе — только текст);
- прямая запись в PIM М.Видео — отдаём контракт API и файл предсказаний, интеграцию делает PIM;
- генерация маркетинговых описаний, ценообразование, ассортиментная аналитика;
- интерфейс для продавца на стороне маркетплейса — **план** после пилота;
- онлайн-A/B-инфраструктура — используем существующую у М.Видео.

## 4. Ключевые сценарии

**С1. Пакетное обогащение каталога.** Выгрузка карточек из PIM → `attrx extract` или `POST /api/extract/batch`
(до 1000 карточек за запрос) → для каждой карточки: категория, атрибуты с каноном, уверенностью, статусом и цитатой →
`accepted` записывается в PIM, `review` — в очередь модерации, `missing` — в отчёт «чего нет в тексте» (запрос продавцу).
Если LLM недоступна, сценарий проходит на правилах, словарях, классификаторе и NER; хвост остаётся в `review`/`missing`.

**С2. Модерация и петля обратной связи.** Модератор открывает очередь (`GET /api/review/queue`, приоритет «вес спроса ×
(1 − уверенность)») → видит значение, альтернативы при конфликте и подсвеченную цитату → подтверждает или исправляет
(`POST /api/feedback` → `outputs/feedback.jsonl`, отмена — `/api/feedback/undo`) → `attrx learn` добавляет исправленные
формулировки в словари (`config/dictionaries/learned.yaml`) → следующий прогон закрывает такие случаи правилами,
без LLM. Правки как эталон и обучающие примеры для NER — **план**.

**С3. Новая категория (холодный старт).** Категорию карточки без id определяет классификатор по тексту. Атрибуты
новой категории берутся из дерева каталога и статистики заполненности и спроса (`attrx prepare` →
`taxonomy_candidates.json`) и описываются в `config/taxonomy.yaml` без изменения кода → правил и словарей ещё мало,
поэтому атрибуты уходят в хвост → LLM извлекает их zero-shot по схеме, с цитатой → **значение только от LLM всегда идёт
на проверку** (`pipeline.UNVERIFIED_ONLY`) → правки модераторов и `attrx build-dicts` пополняют словари → доля вызовов
LLM в категории падает.

**С4. Проверка карточки при загрузке.** `POST /api/extract` по одной карточке → интерфейс модератора собирается под
запрос («покажи только то, что надо проверить, с цитатами») из фиксированного набора компонентов (generative UI,
[GENUI.md](GENUI.md)) → значения на экране берутся из результата пайплайна, а не из ответа LLM.

**С5. Мониторинг качества и откат — план (к пилоту).** Ежедневно по категориям: доля `review` и `missing`, доля карточек
ниже порога классификатора, precision выборочного аудита принятых значений, доля карточек с вызовом LLM. Precision ниже
гейта — категория возвращается в теневой режим.

## 7. Метрики успеха

Общая accuracy не используется: она прячет провалы на редких атрибутах и категориях. Метрики считаются отдельно по
каждому атрибуту; настройка — на dev, результат — на holdout. Основной набор — весь отложенный сплит с эталоном:
23 391 карточка (94 % — хвост каталога; 400 SKU демо-сэмпла исключены); вторичные — стратифицированный набор (2 416
карточек: все 1 372 карточки 12 категорий + 1 044 хвоста, тот же, что в v1) и подвыборка LLM (662 карточки). Режим
в сдаче «+ NER». Протокол — [EVALUATION.md](EVALUATION.md).

**Потолок «только из текста».** В тексте карточек есть 83 % эталонных значений, поэтому micro-F1 по полному эталону
даже при точности 1 не превысит ≈ 0,91 (holdout 0,858). Traffic-weighted F1 этим потолком почти не ограничен: спрос
сосредоточен на бренде и модели, а они есть в тексте у 95–100 % карточек; его потолок ≈ 0,96 (holdout 0,937). Потолок
посчитан по ячейкам holdout (`submission/metrics.json`): 2r / (1 + r) при точности 1, где r — доля эталона ячейки
в тексте или достигнутая полнота, если она выше (диагональ ТВ, например, выводится и из кода модели), с весами спроса.

| KPI | Определение | Holdout, режим в сдаче | Цель | Статус | Где |
|---|---|---|---|---|---|
| K1 Precision автопринятого | доля верных среди `accepted` | 0,954 (95 % ДИ от 0,952); принято 94 % найденного; у самого порога (уверенность 0,70–0,80) — 0,57: 4 % принятого, 38 % ошибок | ≥ 0,95 — гейт выпуска | выполнено для всего потока; слой у порога — в аудит тени (K5) | `submission/metrics.json` (`accepted_precision`), `threshold.json` |
| K2 Автозаполнение | полнота по значениям эталона, которые есть в тексте | 0,927 | ≥ 0,90 | выполнено | `metrics.json` (`recall_extractable`) |
| K3 Traffic-weighted F1 | F1 с весом = доля кликов категории × спрос на атрибут | 0,937 | ≥ 0,90 | выполнено | `metrics.json`, `submission/traffic.json` |
| K4 Справедливость | разрыв F1 между сегментами | М.Видео 0,873 · маркетплейс 0,853 (2,0 п.п.); head 0,870 · torso 0,844 · tail 0,818 (head–tail 5,2 п.п.) | продавцы ≤ 5 п.п.; head / tail ≤ 10 п.п. | выполнено | `submission/segments.json` |

стратифицированный набор: 0,837 → 0,842, без `category_id` — те же 0,842 (классификатор угадал категорию у всех 2 416

На карточку — `ExtractionResult`: `card_id`, `category` и уверенность категории, `category_title`, `category_path`,

## 9. Доверие: контракт против галлюцинаций

1. **Схема.** LLM видит только атрибуты категории; ответ — строгий JSON по схеме, temperature 0.
2. **Справочники.** Допустимые значения — в промпте; значение приводится к канону, вне справочника — отбрасывается
   и попадает в предупреждения как «кандидат в справочник». В JSON Schema список по умолчанию не зашиваем: по замеру это
   провоцирует вынужденный выбор из списка (`LLM_SCHEMA_ENUM`, [LLM.md](LLM.md) §2).
3. **Цитата.** Фрагмент карточки обязателен для каждого значения.
4. **Заземление.** Цитата выравнивается с текстом карточки (числа — точно, слова — с допуском на окончания и знаки),
   значение должно следовать из найденного фрагмента; иначе значение отбрасывается с предупреждением. Смещение
   найденного фрагмента — `evidence_span` (`src/attrx/verify.py`).
5. **Только LLM — только на проверку.** Значение, которое предложила одна LLM, никогда не принимается автоматически,
   при любой уверенности (`pipeline.UNVERIFIED_ONLY` → `Extractor._finalize`; тест
   `tests/test_grounding.py::test_llm_only_value_goes_to_review`). Если LLM подтверждает продавца, правила или NER, её
   голос повышает общую уверенность (noisy-OR), и значение может пройти порог (`::test_llm_corroborating_rules_can_be_accepted`).
6. **Калиброванный порог.** `accepted` — калиброванная уверенность ≥ 0,70 и нет сильного конфликта (при конфликте
   нужна ≥ 0,85); продавец спорит с текстом — `review`; категория определена неуверенно — все значения карточки `review`.
7. **Человек.** Всё сомнительное решает модератор, его правки возвращаются в словари.

Как это выглядит на реальных карточках ([checkpoint/concept.html](checkpoint/concept.html), слайд 5): у смартфона
Redmi A5 (SKU 400633673) диагональ 6,88″ нашла только LLM — уверенность 0,83 выше порога, но значение ушло на проверку;
у iPhone 17 (SKU 402023607) LLM предложила цвет «серебристый» с цитатой «Sage» — проверка заземления его отбросила.
На holdout (подвыборка 662): 61 ответ LLM без опоры в тексте отброшен; из 71 значения одной LLM верны 38 % — если бы их
принимали автоматически, точность каталога упала бы 0,962 → 0,958 ради +0,003 полноты. Правило оправдано замером.

## 11. Экономика

```
C_гибрид     = 1000 · (c_CPU + p_LLM · c_LLM)        — стоимость 1000 карточек
C_LLM_на_всё = 1000 · c_LLM
c_LLM        = T_вх · P_вх + T_вых · P_вых           — токены × цена (on-prem: ₽/ч GPU × время вызова)
C_гибрид / C_LLM_на_всё ≈ p_LLM, так как c_CPU ≪ c_LLM
```

Замерено на holdout (`submission/cost.json`, [LLM.md](LLM.md) §6): LLM зовётся для p_LLM = 31 % карточек; 969 + 52
токена и 3,3 с на вызов (p95 5,0 с, qwen3:4b-instruct на GTX 1060). За 1000 карточек: гибрид — 0,83 ₽ на своей GPU,
20,6 ₽ через GigaChat Lite, 63,2 ₽ через YandexGPT Lite; «LLM на каждую карточку» — 5,6 / 84,6 / 260,2 ₽: гибрид в 4–7 раз
дешевле. Режим в сдаче («+ NER», без LLM) — меньше 0,01 ₽ за 1000 карточек. Прод-сервер с L4 и vLLM — оценка
≈ 11,5 ₽ «на каждую» и ≈ 3,6 ₽ гибрид. Повторный прогон — 0 ₽ (кэш).
Рычаги снижения p_LLM (цель ≤ 20 % пока не достигнута): префильтр «не спрашивать о неупомянутом» (−56 % вызовов
на выборке), LLM только для атрибутов с заметным весом спроса, словари из правок модераторов и из каталога,
дистилляция ответов LLM в NER (план).

## 12. Риски

Пять рисков кейса — галлюцинации, стоимость на масштабе, слабая оценка хвоста, дрейф новых категорий, несправедливость
к продавцам — с мерами и статусом в [RISKS.md](RISKS.md). Продуктовые риски сверх кейса:
- **эталон неполон и местами неверен** — меряем извлекаемый recall и `new_fills`, планируем ручной аудит выборки по редким категориям;
- **модераторы не доверяют автозаполнению** — цитата и уверенность у каждого значения, теневой режим до автопринятия;
- **обязательные атрибуты М.Видео отличаются от наших** — список вынесен в `config/taxonomy.yaml`, правится без кода.

## 13. Допущения и зависимости

- Эталон — атрибуты YML-фида каталога (`vendor`, `model`, `param`): то, что сейчас работает в фильтрах сайта.
- Вход модели — только текст `sku_desc`, без полей фида, чтобы не было утечки эталона во вход.
- Трафик-веса — из `query_clicks` (`attrx traffic` → `config/traffic_weights.yaml`, 255 категорий).
- LLM для разработки — локальная Ollama (qwen3:4b-instruct) и ключ организаторов на ВМ (`OPENAI_API_KEY`, `OPENAI_BASE_URL`).

## Глоссарий

- **accepted / review / missing** — принято в каталог / на проверку модератору / в тексте нет.
- **Coverage** — доля слотов «карточка × обязательный атрибут», где значение заполнено.
- **Извлекаемый recall** — recall только по тем значениям эталона, которые есть в тексте карточки.
- **Traffic-weighted F1** — F1, где атрибуты, по которым чаще ищут, весят больше.
- **Заземление** — проверка, что цитата найдена в тексте и значение из неё следует.
- **Хвост** — атрибуты, которые продавец и правила не закрыли уверенно; только они идут в NER и LLM.
- **dev / holdout** — сплит настройки / отложенный сплит для финальной оценки: на нём ничего не настраивается.
